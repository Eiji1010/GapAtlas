# 自律 Wave 実行ワークフロー

## 目的

1つの Wave（実装単位）を、**実装 → 統合 → 検証 → 第三者レビュー → 指摘対応 → PR → マージ → 引き継ぎ更新**まで自律的に完了させます。

セッションを開始する人間は「次の Wave を実行して」とだけ伝えれば済む状態を目指します。

## 前提

- [並行作業ワークフロー](parallel-agents.md)の Wave 方式に従う
- [第三者レビューワークフロー](third-party-review.md)をレビュー段階で使う
- 現在の到達点は[引き継ぎ](../handoff.md)を正本とする
- ブランチは `main` ← `develop` ← `feature/<内容>`

## 実行手順

### Step 0. 現状把握

```bash
git fetch --all --prune
git switch develop && git pull --ff-only
git log --oneline -10
git status --short
```

`.ai/keep/handoff.md` を読み、**次に実行すべき Wave** と、その Wave のトラック分割を確認する。

`develop` で `make verify` を実行し、**開始時点で緑であること**を確認する。赤い状態から始めない。赤い場合は原因を特定し、修正を最優先の作業とする。

### Step 1. 契約の確認

その Wave の全トラックが依存する型・スキーマ・インターフェースが既に確定しているか確認する。

- 確定していれば Step 2 へ
- 確定していなければ、**契約だけを単独で実装・コミットしてから** Step 2 へ。契約を並列化しない

契約が既に凍結されている場合、**その Wave の実行中に契約を変更しない**。変更が必要になったら並列実装を止めて統合担当が判断する。

### Step 2. 並列実装

トラックごとに worktree 分離エージェントを**同時に**起動する。

各エージェントへ渡す指示に、必ず次を含める。

1. 最初に読むファイル（`AGENTS.md` → `docs/index.md` → 担当領域の仕様書 → 関連コード）
2. **担当ディレクトリの明示**と、担当範囲外を変更しない指示
3. **編集禁止の共有ファイル一覧**（`AGENTS.md` / `CLAUDE.md` / `README.md` / `Makefile` / `backend/pyproject.toml` / `.env.example` / `docs/` 配下 / `.ai/` 配下）
4. 依存ライブラリを追加しないこと（必要なら報告に書く）
5. 実装すべき内容を、**後続が実装できる粒度の契約**として書く
6. 検証コマンド（`cd backend && uv run ruff check . && uv run ruff format --check . && uv run mypy && uv run pytest`）を全て通してから報告すること
7. コミットすること、push はしないこと
8. 報告に含める項目: 作成ファイル一覧 / **実際の公開シグネチャ** / 検証結果（成功・失敗を正確に）/ 指示から意図的に変えた点と理由 / 担当範囲外の変更要望 / 確認が必要な事項 / ブランチ名と worktree の絶対パス

エージェントは**リポジトリの文脈を持たない前提**で指示を書く。会話履歴もセッションメモリも共有されない。

### Step 3. 統合

各トラックの完了報告を読み、次を確認してからマージする。

```bash
git diff --stat develop..<branch>     # 担当範囲外の変更が混入していないか
```

範囲外の変更があれば、マージ前にそのエージェントへ差し戻す。

```bash
git switch develop
git merge --no-ff -m "merge: <内容>" <branch>
```

衝突した場合、解決方針を記録する。トラック分割が誤っていた証拠なので、次の Wave の分割を見直す。

各エージェントから上がった**共有ファイルの変更要望**を、統合担当がまとめて反映する。

### Step 4. 独立検証

**エージェントの自己申告を検証結果として採用しない。** 統合ブランチで自分で実行する。

```bash
make verify
```

失敗した場合は修正してから Step 5 へ進む。赤いままレビューへ進まない。

### Step 5. 第三者レビュー（並列）

[第三者レビューワークフロー](third-party-review.md)に従い、**観点ごとに別エージェント**を同時起動する。

| レビュア | 観点 |
|---|---|
| R1 | 仕様適合（要件の各項目がどのファイル・行で満たされているか） |
| R2 | セキュリティ・信頼性（秘密情報、部分障害、タイムアウト、IAM、入力検証） |
| R3 | 数値正当性・テスト品質（**スコア計算を仕様から独立に再実装して突き合わせる**、境界値、非決定性） |

レビュアへの指示で必ず守ること。

- **実装者の完了報告を渡さない。** 要件の正本（`docs/` 配下）と差分だけを渡す
- **コードを修正させない**（読み取り専用）
- 推測で報告させない。該当行または再現手順を必ず示させる
- 問題が無い場合も、確認した範囲を明示させる

レビュー対象の差分の特定方法を明示する。

```bash
git diff <このWave開始時のコミット>..develop
```

### Step 6. 指摘対応

1. 全レビュアの指摘を重要度順（Critical / High / Medium / Low / Suggestion）に統合する
2. **レビュア間で矛盾する指摘は、自分で検証してから採否を決める**。多数決にしない
3. Critical / High は修正する
4. Medium 以下は採否を判断し、**見送る場合は理由を記録する**
5. 修正後、`make verify` を再実行する
6. 指摘したレビュアへ再確認を依頼する（新規起動ではなく同一エージェントへ継続で投げる）

### Step 7. PR

```bash
git switch -c feature/<内容> develop   # develop で直接作業していた場合
git push -u origin feature/<内容>
gh pr create --base develop --title "<title>" --body "<body>"
```

PR 本文に必ず含める。

- 実装した Wave と Phase
- 変更の概要
- **検証結果の表**（`make verify` の各項目、成功/失敗/未実施を正確に）
- 第三者レビューの指摘件数と、Critical/High の対応結果
- 見送った指摘とその理由
- 未解決事項
- 人間の確認が必要な事項

### Step 8. マージ

```bash
gh pr merge --merge --delete-branch
```

`main` へは直接マージしない。`main` への反映は `develop` からの PR でまとめて行う。

### Step 9. 引き継ぎ更新

`.ai/keep/handoff.md` を**上書き更新**する。履歴は Git が持つので追記しない。

必ず更新する項目。

- Wave の進捗表
- 新たに確定した技術的判断（会話だけに残さない）
- 後続トラックが知る必要のある公開シグネチャの変更
- 持ち越した課題と、それをどの Phase で扱うか
- 未確認事項

コミットして push する。

## 人間の承認が必要な操作

自律実行の対象外です。**必ず止まって確認してください。**

- `main` へのマージ
- `terraform apply`
- 依存ライブラリの追加
- 要件の変更・スコープの拡張
- 秘密情報の取り扱いを変える変更
- 依頼書（`docs/requirements.md`）の「作らないもの」に触れる実装

## 自律実行を止める条件

次のいずれかに当たったら、作業を進めずに人間へ報告してください。

- `make verify` が緑にできない
- レビュアが Critical を報告し、修正方針が要件の解釈に依存する
- 複数のレビュアが矛盾する指摘をし、どちらが正しいか根拠で決められない
- 仕様書（`docs/` 配下）同士が矛盾している
- 実装が「作らないもの」に該当する疑いがある
- 未確認のスキーマ項目に依存しないと実装できない
- 同じ修正を2回試して直らない

**推測で埋めて進めないでください。** 止まって質問するほうが安全です。

## 禁止事項

- 検証を通していないものを「完了」と報告しない
- テストを通すためにアサーションを弱めない
- レビュー指摘を、根拠なく「問題なし」として閉じない
- 強制push・履歴の書き換えをしない
- 他エージェントのコミットを rebase / squash で消さない
